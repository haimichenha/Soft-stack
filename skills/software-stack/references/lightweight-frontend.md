# 轻量、可解释的前端实践

## 先拆开“动态”和“轻量”

- **内容交互**：点击展开、切换面板、输入后更新。组件状态和事件描述这些行为。
- **视觉动效**：悬浮反馈、渐入、移动、连续装饰。简单情况使用 CSS transition/keyframes 即可，React 不是必需的动画引擎。
- **外部同步**：订阅、浏览器事件、定时器等生命周期工作。Effect 不是“视觉特效函数”，不能为了一个可直接计算的显示值滥用 Effect。
- **远程数据**：按现有请求层与后端契约访问。设置本地状态本身不代表发出了网络请求。

“适合小云服务器”至少分为四个预算：构建时资源、服务器运行时 CPU/内存、下载体积/带宽、浏览器 CPU/GPU/电量。静态前端可以由既有后端或静态服务器交付，交互在浏览器运行；这不代表服务端没有网络成本，也不代表大动画对手机免费。

## 按实际栈选择，而不是追新

先读部署版本、package/lockfile 和构建入口。已有客户端 React 应用的展示改造通常不需要额外引入 SSR 服务；若确实有 SEO、首屏或服务端数据要求，再比较架构。不要把 Node 开发服务器直接作为生产方案。

优先级可作为讨论起点，而非所有项目的硬规则：

1. 复用现有布局、组件和 CSS 能力。
2. 复杂编排确实超出现有能力时，评估一个局部动效库及增量体积。
3. Canvas/WebGL、视频、连续粒子仅在效果需求明确且设备预算允许时考虑，提供静态降级。

改造既有认证等表单时保持事件、请求、加载/禁用、错误、重试和跳转契约；演示数据不能伪装成真实可用率或业务指标。

## 从审美语言到可实施要求

把“高级”拆成可观察的版面比例、字体层级、间距、色彩、边框和交互反馈。把“动态”说清楚为：什么触发、哪个元素变化、持续多久、何时停止、减少动态时如何表现。

先用一小块真实组件比较候选。用户未选方向时，不将推荐配色和装饰直接推广到整站。功能需求已经明确且不涉及未决设计的小改动，不必重复要求批准。

遇到素材几何、动作不连续、重复开关或“有运行记录但看不到”的问题，转读 [视觉与动效验收](visual-motion-acceptance.md)，不要仅继续微调 CSS 数值。

## 验证与预算

记录改前和改后的同类证据，预算在测得基线后决定；不得凭感觉宣称“零开销”或虚构跑分。

- 运行相应构建及行为测试；检查包和锁文件差异。
- 在目标桌面/手机视口检查溢出、滚动、触摸区域和字体。
- 检查键盘焦点、标签、错误提示、禁用/加载状态。
- 为装饰动画支持 `prefers-reduced-motion`；避免逐帧用 React state 驱动简单位移动画。
- 动画优先评估 transform/opacity，仍以浏览器观察为准；少用持续的大面积模糊和引发布局的逐帧变化。
- 明确区分模拟接口通过与真实环境通过。未经授权不对生产账号做登录测试。
