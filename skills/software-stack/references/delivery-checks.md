# 软件交付：从代码到用户实际结果

适用于方向探索、原型转产品、调试、既有应用集成、重构和发布；简单代码解释只取调用链，不执行发布流程。这里的规则不依赖语言、框架、MCP 或具体模型。

## 先识别当前阶段，而非强迫一步定稿

| 当前状态 | 有价值的下一产出 | 何时进入下一阶段 |
| --- | --- | --- |
| 目标/样式还模糊 | 少量可比较的方向、最小体验或例子，说明关键差异 | 用户能选出或组合一个值得尝试的方向，不要求所有细节确定 |
| 大方向选定，表示方式未验证 | 针对最重要未知的一小段实现/动作/调用链 | 关键可行性得到证据，知道哪些实现可迁移、哪些仍待选择 |
| 原型已回答主要问题 | 复用原产品的一条最小可运行路径，接入可关闭的改动 | 原接口/路由/错误路径与新能力在同一候选中可验证 |
| 已集成，准备或已经发布 | 对目标版本/环境核对行为及用户效果，局部修正缺口 | 本轮约定结果有相应证据；新问题另列，不冒充全部完成 |

方向可以调整，已确认选择也可被用户撤回；不要为赶进度强行冻结未决项。记录“这轮是否减少了关键未知/形成了决定”，而不是简单计算讨论次数。用户明确只做学习原型时，不强制迁入产品。

### 不确定性不能藏在进度汇报后面

对影响当前交付的未知，用短句交代：**我目前怎么理解 → 哪一点还不确定 → 这轮实际改/没改什么 → 怎样对齐或验证**。

若不同理解会导致不同实现，给两三个有实际区别的对照或询问一个明确点；用户不熟术语时使用视觉/行为差异，不让其先学会术语才能描述。已授权的小范围原型可以先验证可撤回假设，不为低风险细节反复等待确认。

因未决设计暂未改目标模块时，要明确说该项未改及原因，同时推进不依赖该选择的工作。只改亮度、布局或部署而未实现目标表示，必须按实际范围报告。不能从用户看不到变化推断“肯定没改代码”，也不能用“我改过代码”证明已改对效果。

## 1. 找到这次真正修改的对象

定向确认：目标仓库/目录、实际依赖版本、入口、最近已验证状态、正在运行的版本、未提交修改或原始快照。IDE 活动文件、目录名、镜像标签不能单独证明实际执行对象。

现象定位沿一条链：输入/事件 → 状态/数据 → 调用/副作用 → 输出/界面 → 清理。读到通用框架内部却不能解释目标现象时，回到应用调用点、网络 initiator、堆栈或小型复现；仅在问题证据指向依赖时深入。

工具发现先看当前可用的能力与名称。MCP resources 为空不代表服务器没有 tools；不要猜测存在某个文件服务器再逐个枚举无关服务器。适合的工具不可用时，使用已授权的文件/命令能力，或明确说明缺失，不声称调用成功。

## 2. 用最小判别实验调试

记录当前现象、一个假设、能区分它与竞争解释的观察，以及实际结果。尽量一次改变一个关键因素，而不是同时改素材、布局、状态、缓存和部署。

如果用户要求默认就能得到结果，先保留原入口复现，再用单个配置/特性开关作对照。对照开关证明原因，不自动成为最终修复。需要用户多点按钮、多带参数或更改环境时，说明这是改变了使用方式，并确认它是否符合已给出的约定；已有约定清楚时直接按约定处理，不重复询问。

- 有时成功/有时失败：保留一段成功和一段失败的同类输入与状态时间线。
- 用户说仍失败：保留其反馈为未解决，比较环境、版本和操作，而非用“我这里测试通过”否定。
- 连续同类失败且无新证据：停止盲调，改用隔离复现、执行链追踪、契约测试或表示方式验证。昂贵/外部操作的重试预算应在执行前约定，禁止无限重试。
- 已获得明确新证据时继续修复，不把止损规则变成固定两次后放弃。

资源增长或性能异常也可能受观测方式影响。保留原失败，检查调试器、日志对象、探针或自动化句柄是否持有被测对象；保持候选、场景和判据不变，只替换观测方式作有界对照。持有链只是线索，没有对照结果时不直接确认产品泄漏或工具误报，也不为使测试通过而向产品加入清理分支。

## 3. 测试证据与结论一一对应

先从需求或已确认契约写出“哪个入口/默认配置、什么输入、能观察到什么结果”，再审查现有测试的期望值。测试把当前实现的缺失行为也写成通过时，应修正判据，而不是仅增加同类测试。给替代实现、测试夹具或特殊模式下的通过结果标明条件，不将其扩展为用户默认体验已通过。

| 要证明什么 | 合适的证据 | 不能代替它的东西 |
| --- | --- | --- |
| 源码/接口不变量保持 | 明确范围的 diff、AST/契约检查、相关回归 | 只说“没动核心逻辑” |
| 实际行为正确 | 输入→状态→输出，成功/失败/取消/重入测试 | build 成功或日志写了 success |
| 运行成本可接受 | 同机/同场景的时间、节点、请求、内存等测量及测量边界 | 少几个节点或 JS 堆小就宣称显存低 |
| 当前环境已生效 | 该环境的版本/产物读回和真实操作 | 本地文件已保存、上传成功 |
| 用户认可体验 | 用户对指定版本、指定对象的反馈 | 截图存在或模型自己评分 |

后端接口看协议、错误码、数据副作用、幂等/重试；CLI 看参数、退出码、stdout/stderr、文件变化及重复运行。不要要求它们提供浏览器截图。认证、支付或数据写入等边界使用受控夹具/测试环境；真实生产操作须在授权范围内。

测试失败时保留失败记录。若测试标准确实不适合目标，先说明原因并修订标准，再完整重跑；不能拼接不同版本的通过项或悄悄降低阈值来宣布通过。修 bug 时优先让回归测试在修复前暴露问题、修复后通过；不靠匹配某句说明或函数名字证明行为。

验证规模随影响范围变化：文字/局部纯函数改动优先针对性检查；组件状态或视觉改动加真实交互/短片段；共享状态、数据副作用和发布再加入相关回归与恢复验证。没有新证据需求时复用同一版本已有结果，不每轮重跑全部昂贵检查或加载整份项目历史；变更使证据失效的部分必须重验。

## 4. 原型应能逐步迁入产品

原型有两种用途：学习/探索可用独立入口；验证产品集成应复用原组件、路由和接口契约，并替换外部依赖为受控测试响应。明确选哪一种。

每个独立实验先明确它回答哪个未知、成功后接入哪里；解决主要未知且已定位产品入口后，下一交付默认转为真实路径集成，而不是继续完善所有边角。若仍留在独立演示，应说明尚未解决的具体风险或用户明确的学习/探索目标。

建立最小迁移清单：可复用模块、原型专用模拟逻辑、真实接入点、首次集成的验收条件。未解决的局部设计可保留为未决项或在安全开关后继续探索，不让它阻塞整条真实路径。迁入真实组件的本地测试不等于授权生产发布。

将新增展示/能力放在可关闭、可失败的边界上，不把演示用的模拟成功、假导航或内存状态当成产品实现。完成、成功、部分成功、等待二次操作分别处理；装饰不应制造、读取或延迟业务结果。需要改业务契约时明确列为本次改动，不借“展示改造”静默扩大范围。

## 5. 记录状态而不是含糊地说“做好了”

只记录当前任务实际经过的层级，不强迫所有任务逐级填表：

`候选 → 已实现 → 本地验证 → 隔离预览 → 正式生效`

视觉认可、性能证据、用户实际使用反馈、学习掌握度是独立维度。中间候选被新需求替代时标记 superseded，不能因它通过测试就继续部署。

对用户关心的具体功能，一次汇报至少能回答：**实际改动是什么、当前在哪个环境可看、验证到哪一步、还有什么没做到**。若本轮没有修改该功能，直接说明；避免只用“已优化/已更新”概括一切。目标仍有定义分歧时标为未决，不标为完成。

区分“复用/模拟现有能力”和“新增产物”：例如包装器调用不等于实现了新后端，双视图变换不等于补齐多视角素材。声明应能对应到实际文件、接口或可复现输出；没有新增对应产物时直说，不让用户事后寻找不存在的东西。

需要发布时：确认目标和此次授权 → 保留可恢复基线 → 核对构建及依赖 → 在适当隔离环境验证 → 受保护地切换 → 读回目标环境并验证 → 保留回退。

部署方式依项目而定，不把特定代理、容器或云厂商写成通用要求。对不可变资源使用新版本路径；有并发改动风险时用配置/产物指纹守卫，指纹不符就先核对，不覆盖未知修改。测试探针、模拟数据和开发服务不得混入生产包。

涉及外部资源时，分清素材原件/制作记录、运行必需文件和最终发布产物，按交付清单检查实际包含内容，保留应交付的许可或对应源码等材料，不把整个工作目录直接公开。开关关闭、无网络请求或源码未引用，不等于构建包没包含；静态复制等步骤仍可能带入文件。要声称包体缩小或零增量，应比较实际产物清单/体积；运行请求、压缩传输、解码内存是不同成本，分别说明证据。

## 6. 可选执行器与交接

仅在用户要求/适用工作流允许时委派。交付包应有：目标、允许修改的文件、保留边界、实际能力/工具、输入证据、可观察验收、输出格式和停止条件。不要把整份对话、凭据或无关项目文件发送出去。

执行器可以调查或生成局部补丁，但其总结不是宿主验证记录。代码证据、运行结果、未完成项分别返回；未指定授权不切换模型/端点，不因超时重新执行未知副作用。同一文件有并行编辑风险时指定单一写入者。

复用已知的调用状态：持续的模型不存在、权限或额度错误尚未变化时，泛泛的“继续”不应自动重发同一付费任务。先说明阻塞，推进本地可核验部分；只有相关配置/服务状态变化或用户明确要求重试时再进行一次受限尝试。不要把宿主独立完成写成外部模型参与成功。

委派或行为评估应针对一个明确的未知，先选有代表性的小任务；不为显示“全面”而默认复制全部工作或无限追加比较。没有预算/效果证据时不宣称节省额度。达到限额或遇到权限拒绝时停止相关派发，保留已完成部分，不换账户、端点或模型规避；仍可整理和核验不受影响的已有材料。

### 中断续接的最小检查

1. 对照已有状态中的关键版本/产物和实际文件、日志；交接过时则先修正，不照旧计数重复实验。
2. 分开记录执行是否结束、哪些产物可用、哪些验收已通过、哪些交付缺失。例如代码和测试日志存在，但交接说明缺失，仍不能宣称整个任务完成。
3. 宿主可以在授权范围内独立检查部分产物；其结果注明来源，不能补写成原执行器的结论。重试有外部副作用的动作前先读回实际状态。
4. 给出最小、安全的续接点，并说明是继续现有结果、重新验证失效证据，还是需要新授权；不一律重跑所有步骤。

一次验证进展只保存在项目已授权的状态位置。原 AS 与本技能共存时使用一个状态写入控制器，不创建第二份学习账本。对外报告结果、证据链接、未验证边界和下一步，不粘贴整包日志。
